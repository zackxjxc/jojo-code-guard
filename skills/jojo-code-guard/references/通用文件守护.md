# 通用文件守护

本规则适用于所有语言和文本文件。核心目标是让一次局部编辑保持为局部 diff，而不是为每种语言规定一套
编码标准。

## 只读诊断基线

只读诊断编码、BOM、EOL/换行和当前 diff 时，本节不授权任何写入：

1. 确认诊断范围、目标文件和用户要核实的问题。
2. 若任务实际指向本地项目，读取项目根目录 `AGENTS.md`（如果存在）、`.editorconfig` 和可选的
   `.vscode/settings.json`；目标属于 Git 仓库时再读取 `.gitattributes`。
3. Git 仓库执行只读的 `git status --short`、`git diff --stat` 和必要的目标 diff；非 Git 项目直接检查
   目标字节和项目规则，不因缺少 Git 而跳过诊断。
4. 记录编码、BOM、换行、末尾换行和当前差异，区分既有状态与本轮发现；只报告证据，不编辑、格式化、
   转码、暂存或自动修复。

## 修改前基线

修改任何文件前：

1. 确认用户授权范围、目标文件和验收条件。
2. 若任务实际指向本地项目，无论是否属于 Git 仓库，都读取项目根目录 `AGENTS.md`（如果存在）、
   `.editorconfig` 和可选的 `.vscode/settings.json`。
3. 只有目标属于 Git 仓库时，才读取 `.gitattributes`，并执行 `git status --short` 与 `git diff --stat`，
   区分本轮修改和用户已有修改；非 Git 项目不得因此跳过上一步的项目规则。
4. 记录每个已有目标文件的编码、BOM、换行、末尾换行和当前 diff；新文件记录预期规则。

已有未提交修改不等于污染。不得自动恢复、覆盖、删除或重新格式化来源不明的用户内容。

## 写入规则

- 只对授权目标使用最小补丁，不调用会批量格式化、排序、转码或统一换行的工具。
- 老文件保持原编码、BOM、换行和末尾换行，除非用户明确授权迁移。
- 新文本文件优先遵循仓库规则；仓库没有声明时使用 UTF-8 无 BOM，并采用所在目录或项目的主流换行。
- 不根据 `.ts`、`.swift`、`.rs` 等扩展名臆造新的编码策略。formatter 只有在项目已有配置或用户明确要求时
  才运行。
- `.editorconfig` 和 `.gitattributes` 是共享规则；`.vscode/settings.json` 只是可选编辑器提示。发现
  `files.encoding`、`files.eol`、`files.autoGuessEncoding`、`files.trimTrailingWhitespace`、
  `files.insertFinalNewline`、保存时格式化或 code action 可能重写老文件时告警，并报告该设置是否被 Git 忽略
  或纳入跟踪。
- 用户要求批量迁移、安装软件、修改全局配置或大范围规范化时，先说明影响并取得确认。

## 写入后闭环

每次写入后，所有项目都要核对授权目标、本轮实际写入记录，以及目标文件的编码、BOM、换行和末尾换行
是否仍符合编辑前基线或已确认的新文件规则。只有目标属于 Git 仓库时，才执行 `git status --short`、
`git diff --stat`、目标文件 diff 和 `git diff --check`，并检查权限位、文件类型及未授权文件变化。

非 Git 项目应对照编辑前字节基线和本轮文件清单，确认只改变授权字节范围、没有新增或改写无关文件；
不得因 Git 命令不可用而跳过写后验证，也不得把 Git 专用命令当成这类项目的成功条件。

Hook 可用时，`UserPromptSubmit` 记录回合基线，`PostToolUse` 在写入后检查，`Stop` 在回合结束前兜底；
回合开始前已存在且文件指纹未变化的同一诊断标记为 `pre_existing` 警告，本轮改动过的问题、新诊断或基线
不可用仍然阻断。Hook 不能撤销写入，也不是确定性前提；阻断反馈应要求修复后继续原请求，不得用诊断替代
原交付。只有目标属于 Git 仓库时，Hook 未执行才在每次写入后运行：

```text
python "<jojo-code-guard>/scripts/check_diff.py" --repo .
```

发现 `BLOCKED`、整文件变化、纯换行重写或无关文件变化时，停止交付、提交和推送。只有能依据编辑前状态或
Git 基线精确恢复，且不会覆盖用户内容时，才自动做最小修复并复检；否则报告并等待用户决定。

## Git 与编辑器风险

- `core.autocrlf` 或 `core.eol` 可能改写工作区时，先报告并要求在仓库 local 配置中关闭冲突转换，再继续
  写入或暂存；已经丢失的历史换行不能靠猜测恢复。
- Windows 上 `core.filemode` 应为 `false`，避免权限位造成零行内容的 modified。
- 不自动运行 `git add --renormalize`，不修改暂存区，不自动创建 `.vscode/settings.json` 或 `AGENTS.md`。
- `.vscode/settings.json` 缺失只作为可选信息报告；是否跟踪由项目决定。
