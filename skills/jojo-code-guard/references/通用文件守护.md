# 通用文件守护

本规则适用于所有语言和文本文件。核心目标是让一次局部编辑保持为局部 diff，而不是为每种语言规定一套
编码标准。

## 修改前基线

修改任何文件前：

1. 确认用户授权范围、目标文件和验收条件。
2. 若目标属于 Git 仓库，读取根目录 `AGENTS.md`（如果存在）、`.editorconfig`、`.gitattributes` 和可选的
   `.vscode/settings.json`。
3. 执行 `git status --short` 与 `git diff --stat`，区分本轮修改和用户已有修改。
4. 记录每个已有目标文件的编码、BOM、换行、末尾换行和当前 diff；新文件记录预期规则。

已有未提交修改不等于污染。不得自动恢复、覆盖、删除或重新格式化来源不明的用户内容。

## 写入规则

- 只对授权目标使用最小补丁，不调用会批量格式化、排序、转码或统一换行的工具。
- 老文件保持原编码、BOM、换行和末尾换行，除非用户明确授权迁移。
- 新文本文件优先遵循仓库规则；仓库没有声明时使用 UTF-8 无 BOM，并采用所在目录或项目的主流换行。
- 不根据 `.ts`、`.swift`、`.rs` 等扩展名臆造新的编码策略。formatter 只有在项目已有配置或用户明确要求时
  才运行。
- `.editorconfig` 和 `.gitattributes` 是共享规则；`.vscode/settings.json` 只是可选编辑器提示。发现
  `files.encoding`、`files.eol`、`files.autoGuessEncoding`、保存时格式化或 code action 可能重写老文件时告警。
- 用户要求批量迁移、安装软件、修改全局配置或大范围规范化时，先说明影响并取得确认。

## 写入后闭环

每次写入后核对：

1. `git status --short`、`git diff --stat` 和目标文件 diff 范围。
2. 目标文件编码、BOM、换行、末尾换行是否仍符合编辑前基线或已确认的新文件规则。
3. `git diff --check` 是否出现空白错误，是否存在权限位、文件类型或未授权文件变化。

Hook 可用时，`UserPromptSubmit` 记录回合基线，`PostToolUse` 在写入后检查，`Stop` 在回合结束前兜底；
Hook 不能撤销写入，也不是确定性前提。Hook 未执行时，在每次写入后运行：

```text
python "<jojo-code-guard>/scripts/check_diff.py" --repo .
```

发现 `BLOCKED`、整文件变化、纯换行重写或无关文件变化时，停止交付、提交和推送。只有能依据编辑前状态或
Git 基线精确恢复，且不会覆盖用户内容时，才自动做最小修复并复检；否则报告并等待用户决定。

## Git 与编辑器风险

- `core.autocrlf` 或 `core.eol` 可能改写工作区时，先报告；已经丢失的历史换行不能靠猜测恢复。
- Windows 上 `core.filemode` 应为 `false`，避免权限位造成零行内容的 modified。
- 不自动运行 `git add --renormalize`，不修改暂存区，不自动创建 `.vscode/settings.json` 或 `AGENTS.md`。
- `.vscode/settings.json` 缺失只作为可选信息报告；是否跟踪由项目决定。

## 通用实现边界

- 开始修改前分析目标、范围、约束和验收条件，不省略关键实现，不随意偏离项目结构。
- 保持项目现有架构，复用现有函数和依赖，不顺手重构无关代码。
- 新增实现保持清晰、可测试，避免不必要的抽象、依赖、配置和状态。
- 在安全边界和授权范围内，优先满足用户目标与验收条件，其次保持现有行为和架构，再选择复杂度与
  维护成本更低的方案。
- 不为极低概率场景显著扩大威胁模型、权限边界、部署形态、兼容范围或恢复目标。若辅助能力需要新模块、
  外部依赖或高影响配置，先说明成本和最小替代方案并等待确认。
- 低成本、低风险且是当前目标必要前提的补全可以直接实现；辅助能力不得取代主体目标。
- 连续尝试没有新证据，或修改范围和复杂度持续扩大时，停止局部修补并重新评估更简单的方案。

## 通用代码与注释

- 对已有代码实行最小改动，避免重复代码，保持命名清晰；单行默认不超过 120 个字符，确有必要时例外。
- 注释规则只适用于本轮新增或实质修改的代码，未涉及的旧代码不补注释、不整理格式。
- 新增源文件和头文件使用简洁头部注释说明用途；新增或修改的函数、成员和重要状态为非显然约束提供
  简短中文注释。
- 注释不重复代码，不使用“关键局部变量”“函数作用”等模板化措辞。简短片段可不加句号；多行注释先
  概括再补充细节。
- 如无特殊要求，使用中文与用户沟通；代码、标识符和错误信息按需要保留原文。

## 安全、验证与交付

- 不修改未授权文件，不删除已有功能，不改变数据库、权限或外部系统状态，除非用户明确要求并已说明影响。
- 只执行当前任务授权的文件与外部状态变更；超出范围的变更先说明并等待确认。
- 按风险运行测试、静态检查或构建；不虚构结果，无法验证的部分明确说明。
- 交付前检查差异范围，确认没有整文件重排、无关变化或仅换行造成的污染。
- 结论先行，简洁报告修改内容、验证结果、剩余风险和需要用户决定的事项。
- 新生成的说明文档使用 Markdown，表述清晰、技术化；业务逻辑文档说明输入、处理和结果。
