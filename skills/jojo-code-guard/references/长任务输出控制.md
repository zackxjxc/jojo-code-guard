# 长任务输出控制

本规则只在预计产生大量工具输出、长时间构建或测试、反复诊断、大型 Git 差异或大文件读取时加载。
控制进入模型上下文的内容不得降低验证强度、改变命令语义或隐藏失败。

## 输出捕获

- 预计单次输出明显超过 200 行或 16 KiB 时，优先使用工具的摘要、quiet、结果文件或结构化报告能力；
  否则把完整输出保存到权限合适的操作系统临时文件。只有项目已有约定且当前任务允许写入时，才使用
  仓库内的忽略目录。日志不得提交。
- 捕获日志时保留实际命令、真实退出码和耗时；不得让管道、`tee` 或包装脚本掩盖原命令失败。输出可能
  包含密钥、令牌或用户数据时，不得无条件落盘或注入模型上下文。

## 证据读取

- 命令成功时先读取退出码、结果摘要、测试数量、失败数量、警告数量和必要的末尾内容。存在新增警告、
  安全警告、弃用警告或异常耗时时，继续读取有代表性的相关内容。
- 命令失败时保留原始日志，先提取失败目标、错误数量以及最早出现的根因候选。默认展开前 20 个去重后的
  错误；只折叠内容和位置均等价的重复项，不合并不同模块、位置或根因。
- 证据不足时按错误位置读取前后相关区段。单次扩展默认不超过 200 行或 16 KiB，并记录已读范围，避免重复；
  完整堆栈或连续上下文确有必要时可以有针对性地扩大。
- 默认不额外启用 verbose、trace 或 debug；普通输出不足以定位问题时，临时限定到相关模块、测试或时间段。

## 渐进检查

- Git 操作先查看短状态、diff stat、文件列表和有限条数的 oneline log；大文件先检查大小、行数、结构和
  关键词，再读取相关区段。
- 连续三次同类尝试没有产生新证据时，停止重复执行，重新判断根因并选择信息量更高的最小检查。
- 每个阶段只维护一份简短检查点：当前目标、修改文件、关键命令及退出码、未解决问题和下一步。不要反复
  读取或复述已经确认的信息。
- Token 和日志控制不得成为跳过编译、测试、警告审查或必要验证的理由。过滤后的证据不足时，应扩大相关
  范围并明确说明。
- 最终汇报默认包含结论、关键修改、验证命令及结果和剩余风险；用户要求详细日志或审计过程时按要求提供。
